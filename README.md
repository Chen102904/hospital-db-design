# 医院信息管理系统 - 数据库设计

一套完整的医院业务数据库设计，包含 **15 张表**、完整的建表与查询 SQL，覆盖患者管理、**医生排班与号源**、挂号就诊、**候诊叫号**、病历处方、药品库存、收费结算、**药房发药**、**住院登记与出院**、员工与权限、操作日志等核心医疗业务场景。

## 项目简介

本项目基于医院信息系统的实际业务场景，完成数据库的需求分析、表结构设计与 SQL 实现。
设计的出发点是解决真实医疗业务中的数据组织问题：一个患者如何挂号、医生如何接诊、处方如何开立、
药品库存如何扣减并留痕、费用如何结算与退费、患者如何办理入院与出院、以及每一步操作如何留痕可追溯。

业务闭环：**挂号 → 就诊 → 开处方 → 扣库存 → 记流水 → 收费 → 退费（退钱 + 退药）**，
以及并列的住院最小闭环：**办理入院 → 在院观察 → 办理出院**。

## 数据库表结构（15 张表）

| 表名 | 说明 | 关键字段 |
|---|---|---|
| `department` | 科室信息表 | 科室编号、名称、位置、电话、**状态（启用/停用）** |
| `doctor` | 医生信息表 | 医生编号、姓名、职称、所属科室、**状态（在职/离职）** |
| `patient` | 患者信息表 | 患者编号、姓名、身份证号 |
| `registration` | 挂号记录表 | 挂号编号、患者、医生、挂号时间、费用、状态、就诊类型 |
| `medical_record` | 病历记录表 | 病历编号、诊断结果、处方 |
| `medicine` | 药品信息表 | 药品编号、名称、**分类**、规格、价格、库存、**状态（在用/停用）** |
| `prescription_detail` | 处方明细表 | 病历、药品、数量、用法 |
| `medicine_stock_log` | 药品出入库流水表 | 药品、变动类型、数量、变动前后库存、原因 |
| `charge` | 收费单表 | 收费单号、关联挂号（唯一）、挂号费、药费、合计、支付方式、状态、退费信息 |
| `charge_detail` | 收费明细表（费用快照） | 费用类型、项目名称、单价快照、数量、金额 |

| `dispense` | 药房发药记录表 | 关联挂号（唯一）、关联病历、已发药/已退回、药师、发药与退回时间 |
| `admission` | 住院登记表 | 住院号、患者、科室、主治医生、床位、入院时间、出院时间、状态、出院小结、入院/出院办理人 |

## 表关系（ER 说明）

```
department (科室)
    │ 1
    │
    │ N
doctor (医生)
    │ 1                    patient (患者)
    │                      │ 1
    │ N                    │
    │                      │ N
    └──── registration (挂号) ────┘
              │ 1  ↑ 自关联 parent_reg_id（复诊 → 原初诊）
              │
              │ N
    medical_record (病历)
              │ 1
              │
              │ N
    prescription_detail (处方明细) N ──── 1 medicine (药品)
                                              │ 1
                                              │
                                              │ N
                                    medicine_stock_log (库存流水)

patient (患者) ── 1:N ── admission (住院登记) ── 1:1(在当前在院) ── department / doctor
```

**核心关系**：
- 一个科室有多个医生（1:N）
- 一个患者可多次挂号，一个医生可接诊多个患者（挂号表是中间表）
- 挂号表通过 `parent_reg_id` 自关联，表达"复诊对应哪一次初诊"
- 一次就诊产生一份病历
- 一份病历可开多种药品（通过处方明细表关联）
- 每次药品库存变动都记一条流水（可追溯、可对账）
- 一位医生一天一个时段只有一条排班（1:N，靠 `doctor_schedule` 的复合唯一键保证不重复放号）
- 一次挂号占用一条排班号源，一次挂号只发一次药（1:1，靠 `dispense.reg_id` 唯一约束兜底）
- 一次挂号对应一张收费单（1:1，靠 `charge.reg_id` 唯一约束保证不会重复收费）
- 一张收费单含多条费用明细（1:N，挂号费 + 每种药各一条）
- 一位患者可以住多次院，每次住院一条记录（1:N；`patient_id` 上**不加**唯一约束）
- 但同一时间只能在院一次，靠 `admission.current_patient_id` 生成列 + 唯一索引兜底（不是靠代码判断）
- 一个员工产生多条操作日志（1:N）

## 快速开始

### 方式一：用 MySQL（推荐）

```bash
# 依次执行三个 SQL 文件
mysql -u root -p < 01_create_tables.sql
mysql -u root -p < 02_insert_data.sql
mysql -u root -p < 03_queries.sql
```

或在 **MySQL Workbench** 中打开文件，依次点击执行（闪电图标）。

### 方式二：不装 MySQL，用验证脚本

```bash
python verify_sql.py
```
用 Python 内置的 SQLite 验证表结构与查询逻辑是否正确，输出应当是
`建表 35 条 / 插入 9 条 / 查询 39 条，全部通过`。
脚本里做了 MySQL → SQLite 的函数等价替换（`CURDATE`、`NOW`、`TIMESTAMPDIFF`、`DATEDIFF`、`CONCAT`），
所以"报红"只会是真的 SQL 写错，而不是方言差异。

> 注意：SQLite 只能验**语法和查询逻辑**；生成列、CHECK 约束、`SELECT ... FOR UPDATE` 行级锁
> 这些 MySQL 特性的**行为**，还是要在 MySQL 8.0 里验证（`seed_demo_data.py` 导入时的断言就在做这件事）。

60 名患者 / **60 种药品（11 个分类，覆盖抗感染、心血管、消化、呼吸、内分泌、解热镇痛、神经、维生素、
注射输液、中成药、皮肤五官；其中 58 种在用 + 2 种停用③）** / 333 条医生排班（含今天起 3 天在职医生放号）/
180 条挂号（含 30 条复诊）/ 125 份病历 / 255 条处方明细 / 324 条库存流水 / 85 张收费单
（80 张已收费、5 张已退费）/ 262 条收费明细 / 78 条发药记录（76 条已发药、2 条已退回）/
**28 条住院登记（7 条在院、21 条已出院）** / 5 个员工账号 / 15 条操作日志。

挂号状态分布：已发药 76 / 已挂号 48 / 已就诊 40 / 已取消 7 / 已退费 5 / 已收费 4。

> ① 停用科室 = 眼科；② 离职医生 = 马文、曹涛（他们名下的历史挂号与病历保留，但不再出现在新增下拉里，
> 也不再排新班）；③ 停用药品 = 氯雷他定片、氧氟沙星滴眼液（历史处方仍在）。
> 这三类"停用样本"是故意留的：用来演示"主数据只停用不删除，历史数据不受影响"。

随机种子固定，所以**今天以前的历史数据每次执行完全一致**（连跑多次逐条核对过）。
只有「今天」的记录会随执行时刻推进而变化：一来"今天"可用的时间段会变长，
二来演示数据必须保证不晚于此刻，所以同一天上午和傍晚各跑一次，今天的条数会有少量浮动，
属正常现象。换一天再跑同理。
老库缺少的字段和表会自动补齐。

> 演示数据的两个自洽性保证：
> 1. 所有时间（挂号、病历、库存流水、收费、退费、住院、日志）都断言不晚于"此刻"，页面上不会出现未来时间；
> 2. 库存流水是**事件驱动**滚出来的——期初建账入库、处方扣减出库、退费退药入库三类事件按时间排序后
>    逐条算出"变动前 / 变动后"，脚本内断言"期末库存 == 声明的当前库存"。
>
> 住院数据另有一条硬保证：同一位患者**最多只有一条"在院"记录**（唯一索引兜底），脚本生成时也会断言，
> 不存在"一个患者在院两次"的脏数据。

| 分类 | 语句 | 考察点 |
|---|---|---|
| 基础查询 | 单表查询、多表联查 | JOIN、WHERE |
| 数据操作 | 插入、修改、删除 | INSERT/UPDATE/DELETE |
| 统计聚合 | 分组统计、计数、求和 | GROUP BY、COUNT、SUM |
| 排序分页 | TOP N、分页查询 | ORDER BY、LIMIT、OFFSET |
| 子查询 | 高于平均值的记录 | 嵌套子查询 |
| 条件筛选 | 日期范围、库存预警 | BETWEEN、比较运算 |

## 核心设计要点

1. **外键约束保证数据一致性**：挂号表关联患者、医生、科室，处方明细关联病历与药品，收费单关联挂号与患者，住院登记关联患者、科室、主治医生，删除或修改主表数据时受约束保护
2. **索引优化查询性能**：为挂号时间、状态、排班编号、就诊时间、患者电话、收费时间、日志时间、排班日期、发药时间、住院时间等高频查询字段建立索引（共 20 个）
3. **中间表设计**：挂号表作为患者与医生的关联表，处方明细表作为病历与药品的关联表，符合数据库范式
4. **自关联外键**：`registration.parent_reg_id` 指向同表主键，表达"复诊关联哪一次初诊"
5. **事务保证业务原子性**：开处方要同时写病历、写明细、扣库存、记流水，放在一个事务里保证要么全成要么全不成
6. **库存流水可对账**：每次变动记录变动前后库存，从期初顺着流水加减必须等于当前库存
7. **号源不超卖**：`UPDATE doctor_schedule SET booked_count = booked_count + 1
   WHERE schedule_id=? AND status='正常' AND booked_count < total_quota`，
   把"判断还有没有号"和"占一个号"压成一条语句，并发下也只有一个人能成功
8. **费用快照**：收费明细存的是收费那一刻的单价与数量，药品调价不会篡改历史账目
9. **权限与审计**：员工表存角色、密码只存哈希；操作日志记录"谁、何时、对哪条数据、做了什么"
10. **正反流程都有账**：发药记一条 `dispense`，退费时置为「已退回」并填退回时间，药品同时退回库存
11. **用生成列 + 唯一索引实现"部分唯一索引"**：住院表上
    `current_patient_id INT GENERATED ALWAYS AS (IF(status='在院', patient_id, NULL)) STORED`
    加 `UNIQUE (current_patient_id)`——唯一索引不约束 NULL，于是"在院最多一条、出院可以有很多条"这个
    业务规则由数据库直接保证，不依赖应用层"先查再插"（并发下先查再插并不可靠）
12. **CHECK 约束守住不变式**：`ck_adm_time` 保证出院时间不早于入院时间，`ck_adm_discharge` 保证
    "状态"与"出院时间"互相一致（在院必须没有出院时间，已出院必须有），脏数据根本写不进库
13. **中文支持**：使用 utf8mb4 字符集，支持完整的中文字符存储
14. **主数据用状态位而不是物理删除**：`department` / `doctor` / `medicine` 三张表各有一个状态列
    （启用/停用、在职/离职、在用/停用），`staff` 用 `status TINYINT`。它们都被历史业务数据引用着
    （科室牵着医生、医生牵着病历、药品牵着处方），硬删要么被外键挡住、要么把历史记录毁掉；
    用状态位则能表达"不再接新业务，但过去照常可查"。停用的记录只在**新增时的候选下拉**里消失，
    列表页、历史病历、统计报表、导出的 Excel 全部照常显示。
